# Case-insensitive name matching happens in Python, not SQLite

Names the app compares without regard to case (people search on Pick your name, and the rule that room names are unique within an office) are matched with Python's `str.casefold()` over the rows read from the database, not with SQLite's `lower()` or `COLLATE NOCASE`, because SQLite folds only ASCII: in story 1.1's review, `lower('Ó Briain')` returned `'Ó briain'`, so a search typed in another case missed accented names that HR's real list will contain (plan `story-pick-and-switch-your-name-end-to-end-plan.md`, Review Triage Log #3; commit `cf77262`). Story 1.2 applied the same rule to room names: the service trims and casefolds to detect a duplicate, and the database keeps the exact-match unique constraint `uq_rooms_office_id_name` only as a backstop, with an `IntegrityError` mapped to the same refusal (plan `story-office-managers-manage-their-office-s-rooms-plan.md`, Design Notes; commit `d2a5b1f`). The trade-off is that matching reads every active person or every room in the office into Python, which the plans judged cheap at a few hundred rows, and that the database alone does not enforce case-insensitive uniqueness, so two concurrent adds differing only in case could both commit; neither plan states a reason for not adding a casefolded column with a unique index instead.

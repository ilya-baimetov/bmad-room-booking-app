- (decision) AD-1 Paradigm: layered modular monolith. One FastAPI app; feature modules people, rooms, bookings, calendar; each module web -> service -> store. Binds all epics. Prevents epics placing logic in routes or reaching into each other's tables. Rationale: 300 users, one team, one DB; layers keep rules testable without HTTP.
- (decision) AD-2 Rendering: server-rendered Jinja2 pages, htmx 2 for partial swaps; no SPA, no JS build, no public JSON API in release one [ASSUMPTION]. Alternatives weighed: React SPA + JSON API (two codebases, build step, overkill), plain full-page forms only (fails sheet/panel feel). Prevents epic 1 picking a SPA while epic 2 renders HTML.
- (decision) AD-3 Data ownership: offices and people written only by the seed loader; rooms only by rooms module; bookings and booking_attendees only by bookings module. Other modules read through the owner's service functions. Calendar has no store. Prevents two owners of bookings and epic 3 writing its own booking queries.
- (decision) AD-4 Overlap and closed-room refusal enforced in SQLite: BEFORE INSERT and BEFORE UPDATE triggers on bookings RAISE(ABORT) when another booking of the same room overlaps (half-open [start, end)) or the room is closed; booking writes run in BEGIN IMMEDIATE transactions; service maps the abort to BookingConflict / RoomClosed. Rationale: SQLite has no exclusion constraints; single writer serialises IMMEDIATE transactions, trigger guarantees RULE-1 on every code path incl. concurrent requests. Service pre-checks allowed for messages, never the only guard.
- (decision) AD-5 Time: booking instants stored as UTC ISO-8601 text 'YYYY-MM-DDTHH:MM:00Z' (lexical order = time order); conversion to Europe/London only in the web layer via zoneinfo; 15-minute alignment and 15 min to 4 h length checked in bookings service plus CHECK (end > start). UK offsets are whole hours so alignment holds in UTC. Prevents mixed naive/aware times across epics and DST bugs.
- (decision) AD-6 Current person: cookie person_id (integer people.id), long-lived (400 days, browser max), unsigned since RULE-6 lets anyone pick anyone; one FastAPI dependency current_person reads it, redirects to Pick your name when missing or unknown; no other code reads the cookie. Prevents three ways of knowing who is acting.
- (decision) AD-7 Authorisation in services: RULE-3 and RULE-4 checked in service functions that take the acting person; templates hide controls using the same predicates (can_change_booking, can_manage_office) but are never the only guard. Office manager of office X = people.is_office_manager and people.home_office_id = X. Prevents UI-only checks and differing manager definitions.
- (decision) AD-8 Attendee visibility (R15): bookings service returns a booking view whose attendees are filled only for organiser, attendees and managers of the room's office; otherwise none. Templates never load attendees themselves. Prevents calendar and rooms grid leaking attendees differently.
- (decision) AD-9 Seed loading: one CLI command loads offices and people from one CSV format, upserting by a stable external key (email) [ASSUMPTION] so people.id survives reloads (cookies and bookings stay valid); a person missing from a later file is marked inactive, never deleted [ASSUMPTION]; HR's list loads the same way.
- (decision) AD-10 Schema changes only through Alembic migrations, including the AD-4 triggers; migrations run as a deploy step before the app starts.
- (decision) AD-11 Deployment: exactly one app instance on one host, a container with a local persistent volume holding the SQLite file (WAL mode, busy_timeout); never horizontally scaled, never on network file storage; Caddy terminates HTTPS; Litestream replicates continuously to off-host object storage. Reach limited to company networks (office Wi-Fi, VPN) [ASSUMPTION] because there is no sign-in and staff names are personal data. Provider: a small Linux VM in a UK region, company-run or cloud [ASSUMPTION]. Alternatives weighed: PaaS with ephemeral disk (loses SQLite), Postgres (violates RULE-7).
- (decision) AD-12 Errors: domain errors are exception classes raised by services (BookingConflict, RoomClosed, NotAllowed, InvalidBooking); one handler maps them to 409/409/403/422 and renders the message partial in EXPERIENCE voice. Prevents per-route error shapes.
- (decision) AD-13 Cancelling deletes the booking and its attendee rows; bookings has no status column [ASSUMPTION, revisit with OQ-3 retention]. Prevents epic 3 having to know a cancelled-state filter epic 2 invented.
